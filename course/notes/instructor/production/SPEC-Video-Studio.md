## What this is

A small web app that takes `GUIDE-NN.md` and produces a finished YouTube video: animated
boxes-and-arrows diagrams that look designed rather than drawn, cut to a voiceover recorded by
Fernando.

**Not** a general video editor. It does one thing: this course's lessons.

## The chain

```
  course/guides/GUIDE-01-*.md            ← the source of truth, already written
        │
        │  (1) EXTRACT — the ASCII blocks, headings, callouts and tables
        ▼
  scenes/guide-01.json                   ← the scene spec. Lives in git, next to the guide
        │                                   generated by an LLM, corrected by hand
        │  (2) RENDER
        ▼
  React components                       ← React Flow nodes + edges, text cards, code blocks
        │                                   ONE component tree
        │  (3) COMPOSE
        ├──────────────────► Remotion Player  → the editor, in the browser
        │                                     → and the website's interactive diagram
        │  (4) RENDER
        ▼
  out/guide-01.mp4 (1920×1080)  +  .srt  +  chapters.txt  +  shorts/*.mp4
        ▲
        │
  audio/guide-01/scene-03.wav            ← your voice, recorded per scene
```

## The four decisions that matter

### 1. The intermediate artifact is **data, not code**

The LLM generates `scene.json`, never React source.

| | Generated JSON | Generated React code |
|---|---|---|
| Reviewable | A human reads 30 lines and sees the diagram | Reading a component to picture the output |
| Diffable in git | Cleanly | Noisily |
| Fixable by hand | Edit a label, done | Read the code first |
| Can it break the build | No | Yes |
| Regenerable | Freely | Risky — hand edits get overwritten |

Same reason the guides are the source of truth: **content is data, rendering is code.** Code is
written once and reviewed; data is generated per guide.

### 2. One component tree, two outputs

The React component that draws the client/server diagram is the *same* component whether it is:

- a frame in the rendered MP4 (via Remotion), or
- an interactive diagram on the course website (via React Flow directly).

That is the payoff for choosing React over a dedicated animation tool. Write the diagram once,
get the video **and** a diagram the student can hover and click on the lesson page. Motion Canvas
cannot do the second one.

### 3. Scene duration comes from the audio, not from a number

Each scene's length is **derived from the length of its voiceover file**. Never hardcoded.

This is what makes re-recording cheap: you re-record scene 6, drop in the new `.wav`, and the
timeline re-flows. Hardcode durations and every re-record becomes a manual re-edit — which is
exactly how a course stops being maintained.

### 4. The tool lives in this repo, beside the course

> **Revised 19 September.** This originally said the tool should get its own repository, to keep
> a Node toolchain out of the course repo. In practice the two are edited in the same sitting and
> the split meant hardcoded sibling paths that broke if either folder moved. One repo, one clone.

| Where | What |
|---|---|
| `video-studio/` | The app: React, Remotion, render pipeline. `node_modules` gitignored |
| `video-studio/scenes/` | The scene specs — content, reviewed like guides |
| `course/video/audio/` | Voiceover |
| `course/video/out/` | Rendered video. Gitignored: derived, rebuilt on demand |

Content is still rebuilt rather than migrated; it just does not need a second clone to do it.

## The scene spec

The whole design rests on this being simple enough that an LLM emits it reliably and a human
reads it at a glance.

```jsonc
{
  "guide": "GUIDE-01",
  "title": "What Is a Web App? Frontend and Backend",
  "theme": "course-dark",
  "scenes": [
    {
      "id": "client-server",
      "kind": "diagram",              // diagram | text | table | code | screencast
      "source": "GUIDE-01 §1",        // traceable back to the guide
      "audio": "scene-02.wav",        // duration derives from this
      "nodes": [
        { "id": "browser", "label": "BROWSER\n(client)", "at": [0, 0],   "accent": "blue" },
        { "id": "server",  "label": "SERVER",            "at": [520, 0], "accent": "green" }
      ],
      "edges": [
        { "from": "browser", "to": "server", "label": "give me the videos", "appearAt": 1.5 },
        { "from": "server", "to": "browser", "label": "here they are",      "appearAt": 4.0 }
      ],
      "captions": [
        { "at": 0.0, "text": "Every web application is two programs..." }
      ]
    }
  ]
}
```

`appearAt` is seconds into the scene. That single field is what syncs the picture to the voice,
and it is the one thing worth getting right.

## Looking like Miro, not like Mermaid

This is a styling problem, not a tooling one, and it is where "looks cool" is won or lost.

| Choice | Decision |
|---|---|
| **Diagram engine** | **React Flow** — nodes and edges as data, which is exactly what we generate. Narrowly built for flowcharts, which is what we draw |
| Layout | Explicit coordinates in the spec. Auto-layout looks auto-laid-out |
| Look | Generous padding, rounded corners, one soft shadow, two-tone accents per role (client / server / data), one typeface, a real grid |
| Motion | Nodes fade and rise a few pixels; edges draw along their path; nothing spins |
| Restraint | No more than 5 boxes on screen. GUIDE-01's map has three — that is the ceiling, not the target |

> **tldraw** is the other candidate: a Miro-style infinite canvas with a programmatic editor API,
> and better if you ever want to grab a diagram and rearrange it by hand. It is heavier for the
> generate-and-render path. **React Flow first; revisit tldraw if hand-tweaking becomes the
> bottleneck.**

## Distribution formats

You flagged format as important, so it is a first-class output, not an export afterthought.

| Output | Spec | Why |
|---|---|---|
| **Main** | 1920×1080, 30 fps, H.264, AAC | YouTube standard |
| **Chapters** | `chapters.txt`, timestamps from scene boundaries | Free, and scene titles already exist in the spec |
| **Captions** | `.srt` generated from the `captions` field | Already in the spec. Also feeds search |
| **Shorts** | 1080×1920, selected scenes, ≤60 s | Same components, different composition. A single self-contained scene — the golden rule, the status codes — is a Short |
| **Thumbnail** | 1280×720 still, rendered from a title component | Consistent across 65 videos without opening Photoshop |

Shorts being nearly free is the strongest argument for the whole approach: the same scene spec
produces a lesson and a piece of distribution.

## The editor — what the app actually looks like

```
┌──────────────┬────────────────────────────────────┬───────────────┐
│  SCENES      │   PREVIEW  (Remotion Player)       │  PROPERTIES   │
│              │                                    │               │
│ 1 Title      │   ┌─────────┐      ┌─────────┐     │ kind: diagram │
│ 2 Client/svr◄│   │ BROWSER │─────►│ SERVER  │     │ audio: 02.wav │
│ 3 Restaurant │   └─────────┘      └─────────┘     │ 6.4s (from    │
│ 4 FE / BE    │                                    │    audio)     │
│ 5 Golden rule│                                    │ nodes  [ + ]  │
│ ...          │                                    │ edges  [ + ]  │
├──────────────┴────────────────────────────────────┴───────────────┤
│ ▶  ────●──────────────────────────────────────────────  02:14     │
│    [audio waveform, scene boundaries marked]                      │
└───────────────────────────────────────────────────────────────────┘
  [ regenerate from guide ]   [ attach voiceover ]   [ render ]
```

`@remotion/player` is the preview — the same composition that renders to MP4, playing in the
browser. That is why this is a small app rather than a video editor: **we are not building
playback, compositing or encoding.** We are building a list, a form and a render button.

## Open questions

- **Who writes the voiceover script?** The guide is written to be read, not spoken. A separate
  script per scene is probably needed — that is the `captions` field doing double duty.
- **Where does the screencast fit?** Shot 9 of GUIDE-01 is real DevTools footage. Remotion can
  embed a video file in a composition, so it is a scene of `kind: "screencast"` — but the
  recording is still manual.
- **How long is a video?** GUIDE-01 is ~16 minutes. Per-section videos of 4–5 minutes may be
  better for attention and are definitely better for re-rendering.
- **Does the website embed the MP4 or run the React Flow diagram live?** Decision 2 makes both
  possible. Live is more impressive and harder to get right on mobile.
